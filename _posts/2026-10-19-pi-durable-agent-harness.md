## 为什么需要一个 Harness

个人使用的 coding agent 会话，通常有着自然的生命周期：打开终端，交代任务，查看结果，需要时再回到历史会话。

如果 Agent 开始服务一个团队，情况就不同了。

它可能同时处理 Slack 频道里的多个讨论，在后台运行几项搜索，让不同成员从网页、终端或手机接入。期间还会经历进程重启、应用发布，甚至机器故障。

这时，重新打开对话只是恢复工作的第一步。系统还要知道哪些任务正在运行，它们执行到了哪个阶段，哪些输入已经进入队列，以及某个外部请求到底有没有完成。

过去，这些逻辑往往要由每个 Agent 应用自己实现。Pi Durable 把对话、任务、应用状态和恢复规则放进同一个 Harness，希望为长时间运行的 Agent 提供一套统一的底层机制。

它建立在 `pi-ai` 的模型访问能力之上，面向的是新的 Agent 应用，并不是用来替代 Pi coding agent。

## 恢复的不只是上下文，还有执行状态

Transcript 会记录用户消息、模型回答、工具调用和工具结果。这些记录很重要，它们说明系统已经发生过什么。

但一段完整的 Transcript，并不会自动变成任务调度器。它无法单独告诉新进程：哪个任务还没结束，它正在等什么，恢复以后应该从哪一步继续。

Pi Durable 因此把几类状态一起保存：

- Transcript entries 记录已经提交的消息、调用和结果；
- Task records 记录任务的检查点、所有权和等待关系；
- Documents 与 Submissions 保存应用状态、实时进度和排队中的输入。

![Pi Durable 保存对话、任务和应用状态，并在新进程中恢复调度](/assets/images/14-pi-durable/01-recovery-map.png)

*图 1：Pi Durable 的恢复流程。图表结构与内容来自 StackToHeap 原文。*

新进程打开同一份持久化存储以后，可以重新安装任务定义并启动调度。已经完成的任务保持完成，未结束的任务则根据保存的检查点继续运行。

这里的检查点不是被冻结的 JavaScript 调用栈。它是一份写入存储的状态，任务代码要根据这份状态决定下一步该做什么。

假设 Agent 已经完成 Issue 查询，又在部署途中退出。恢复时，系统可以保留查询结果，并找到那次被打断的部署调用，不必让模型只看聊天记录，再猜一遍整个流程。

至于部署到底有没有发生，则是另一个问题。后文还会看到，这是 Durable Agent 最需要谨慎处理的边界。

## Commit 是最重要的边界

Pi Durable 的关键不只是把不同记录写进数据库，而是让相关变化进入同一次 Commit。

一次 Commit 可以同时追加 Transcript entry、更新 Task record，并修改有类型的 JSON Document。存储要么接受整组变化，要么一个都不接受。只有存储确认以后，Harness 才把新状态交给客户端和调度器。

比如，一个代码审查任务准备结束时，可以在同一次 Commit 中完成三件事：写入审查发现，把任务标记为完成，并在计划文档中勾掉“代码审查”。

![审查结果、任务状态和计划文档在同一次 Commit 中更新](/assets/images/14-pi-durable/02-atomic-commit.png)

*图 2：一次审查完成提交包含的三类状态。图表结构与内容来自 StackToHeap 原文。*

这样可以避免一些很难解释的中间状态：计划上显示审查完成，任务却仍在运行；或者界面已经展示完成消息，存储里却没有对应的审查结果。

流式输出也遵循相同思路。模型的部分回答和工具的运行输出，会以进度状态持续提交。进程退出后，最后一次成功提交的内容仍然存在；尚未提交的部分则可能丢失。

对重新连接的客户端来说，这带来了一个很重要的约束：**它看到的状态，应当是已经提交的状态。**

## Pi Durable 的基本组成

理解了 Commit，Pi Durable 里的几个名称就容易区分了。

| 概念           | 负责什么                        |
| ------------ | --------------------------- |
| Harness      | 打开存储，运行对话与任务调度              |
| Conversation | 一条带独立 Agent 配置的对话记录         |
| Entry        | 不可变的消息、结果、Reset 或自定义记录      |
| Submission   | 已被系统接收、可以等待结果的输入或写入         |
| Document     | 通过 Commit 更新的有类型 JSON 状态    |
| Task         | 带检查点、所有权和执行结果的持久化状态机        |
| Registry     | 当前进程安装的 Extension 与 Task 定义 |

这里的 Agent 指一条 Conversation 使用的配置，包括模型、推理级别、指令、工具、Extension 和工作目录。不同 Conversation 可以采用不同配置。

Extension 则把工具、Prompt 片段、Hook、Wrapper 或 Task 组合起来。Hook 可以修改模型请求，也可以拦截一次工具调用。

需要注意的是，存储里保存的是 Extension 和 Task 的名称及状态，不是它们的完整代码。进程重启以后，宿主应用仍要安装未完成任务需要的定义。保存下来的旧检查点，也必须能被新代码理解。

存储方式之间的区别也值得注意。`MemoryStorage` 适合测试，但进程退出后数据随之消失。SQLite 和 JSONL 可以重新打开。持久化完整历史，也不意味着每次模型请求都要携带全部历史：Compaction 可以压缩模型当前看到的上下文，同时把更早的记录继续留在存储中。

## 模型与工具循环如何变成任务

Pi Durable 可以接管模型与工具之间的循环。

一条输入先作为 Submission 被接收，Generation Task 调用模型。如果模型请求调用工具，工具调用会变成子任务；工具结果提交以后，系统再进入下一轮 Generation，直到产生最终回答。

```text
接收输入
  → Generation Task
    → 模型返回工具调用
      → Tool Tasks 提交结果
    → 下一轮 Generation
      → 最终回答，Submission 结束
```

一次 Turn 是一轮模型响应及其工具调用。一次 Run 则从用户输入开始，经过若干 Turn，直到最终回答结束。模型生成、工具调用和上下文压缩，都可以使用同一套任务机制。

文件和进程操作通过 Execution Environment 完成。宿主可以接入本机环境，也可以为每条 Conversation 提供容器或其他远程环境。

但改变工作目录并不会自动形成安全边界。保存一个外部 Agent 的协调检查点，也不会让那个外部运行时自动获得恢复能力。权限、隔离和外部系统的状态，仍然要由应用自己处理。

## 恢复是一种策略，不是盲目重放

只要任务会修改外部系统，就会遇到一个绕不开的时间窗口：

```text
提交操作意图 → 执行外部操作 → 提交操作结果
```

意图说明任务准备做什么，结果说明外部系统返回了什么。真正的部署、付款或消息发送，发生在 Pi Durable 存储事务之外。

![外部部署已经接受请求，但任务尚未提交结果时进程退出](/assets/images/14-pi-durable/03-deployment-crash-window.png)

*图 3：外部副作用与持久化状态之间无法完全消除的中断窗口。图表结构与内容来自 StackToHeap 原文。*

图中的部署服务已经接受请求，但 Agent 还没来得及保存结果，进程就退出了。重新打开存储时，系统只能看到“准备部署”的意图，看不到最终结果。

同一份检查点，可能代表请求还没发出去，也可能代表部署已经在远端运行。仅靠本地存储，无法区分这两种情况。

应用需要为不同工具选择恢复策略：

- **安全重试**：外部服务支持幂等键，恢复时继续使用同一个键；
- **查询状态**：保存远端操作标识，重启后先查询操作是否已经执行；
- **记录中断**：不自动重复操作，把不确定状态交给应用策略或人工核对。

Pi Durable 中声明了 `replay: "safe"` 的工具，可以在中断后重新执行。没有声明安全重放的工具，不会被框架盲目重跑；模型会得到一个 interrupted 结果，以及中断前已经提交的输出。

这个标记不是框架替工具做出的安全证明，而是工具作者给出的契约。部署、付款和发消息能否重试，仍取决于外部服务有没有幂等键、状态查询或补偿机制。

`requestId` 也有明确边界。它可以避免客户端把同一条 Submission 重复放进队列，却不能保证这条输入触发的所有外部操作都只执行一次。

Pi Durable 做的，是让这些不确定性变得可见，并为恢复策略提供一个可以保存状态的位置。它不承诺外部副作用天然具备 exactly-once 语义。

## Subagent 也有所有权和生命周期

在 Pi Durable 中，一个 Subagent 可以表现为由工具任务创建并拥有的独立 Conversation。它有自己的 Agent 配置，也使用同一套持久化机制。

![主对话、委派任务、子对话和子任务之间的所有权关系](/assets/images/14-pi-durable/04-subagent-ownership.png)

*图 4：Subagent 工作的所有权关系。图表结构与内容来自 StackToHeap 原文。*

应用仍然要编写负责委派的工具。为了在恢复时避免重复创建 Subagent，这个工具需要找到已经存在的子 Conversation，并使用稳定的 `requestId` 重新接上原来的输入。

所有权让取消操作有了明确方向。前台任务被终止时，它拥有的子任务可以按层级清理；任务也要等到自己拥有的工作全部结束，才能标记为完成。

后台任务的生命周期有所不同。它不会一直占用父任务当前的 Run，也能在父任务的常规取消之后继续工作，再通过 Follow-up 把结果送回来。

所以，“你继续和主 Agent 聊，我在后台研究”不只是多发起一次模型请求。后台工作需要持久身份、明确的所有者，以及完成后的返回路径。

## 同一条 Conversation，可以由多个界面接入

浏览器不必拥有任务的生命周期。

Pi Durable 可以提供一份已经提交的 Conversation view。客户端接入时先获得当前状态，再订阅后续更新。后来加入的终端、网页或手机，不需要从第一条事件开始回放，也不依赖之前的页面一直保持连接。

当 Conversation 正忙时，新的输入可以进入队列。Follow-up 会在之后启动新的 Run，Steering 则可以在工具轮次的边界加入当前工作。

这里还有一个容易混淆的区别：取消等待，不等于取消任务。关掉网页或放弃一次客户端等待，断开的只是这次等待本身；要真正停止 Submission 或 Conversation，必须明确执行终止操作。

多端接入也不等于框架已经提供完整的多人协作产品。谁可以查看对话，谁可以 Steering，多个用户的指令发生冲突时如何处理，仍要由宿主应用定义身份、权限与协作规则。

## Durable 不等于能力被冻结

长时间运行的 Agent 不可能永远使用同一套工具实现。

Pi Durable 允许进程用同名 Extension 替换 Registry 中的定义。已经开始的工具调用继续使用启动时的实现，后续阶段或新的调用可以使用更新后的版本。进程重启以后，保存的任务会根据新进程安装的定义继续解析。

这为运行中的 Agent 改进工具和工作流留下了空间，但它不是自动迁移系统。

旧检查点是否兼容新代码，Task 版本如何迁移，升级失败后怎样回滚，都需要应用明确处理。由 Agent 生成的新工具也不能写完就立即替换线上能力，仍然需要测试和清晰的启用步骤。

## 宿主应用仍然要完成哪些工作

“Durable”不等于进程永远在线，也不等于存储永远不会丢失。

| 边界          | 宿主应用的责任                |
| ----------- | ---------------------- |
| 进程退出        | 监督并重新启动进程，打开原存储并恢复调度   |
| Storage 所有权 | 保证一份存储由一个进程拥有，避免并发写入冲突 |
| 外部副作用       | 提供幂等重试、状态查询、补偿或人工核对    |
| 用户与工具权限     | 提供认证、授权和执行环境隔离         |
| 存储丢失与升级     | 备份数据，验证版本及检查点兼容性       |

截至 2026 年 10 月，官方 README 仍明确把 Pi Durable 标记为实验性项目，API 可能在不同版本之间发生变化。StackToHeap 原文中的实验使用 `@earendil-works/pi-durable`、`pi-ai` 和 `chord` 1.0.2，文章解释的是设计概念，不是一份当前版本的 API 教程。

如果要把它用于真实系统，仍然需要锁定版本，并验证自己的工具、任务、Storage Adapter 和恢复策略。

## Harness 的未来可能是什么

从 Pi Durable 的设计可以看到，Agent 应用正在出现更清楚的分层：

```text
模型            = 推理与工具选择
Pi Durable      = 已提交状态、任务所有权与恢复机制
应用代码        = 能力、策略与外部系统集成
交互界面        = 工作状态的入口，而不是任务的生命周期
```

模型仍然负责判断和选择工具，但连续性不能只靠模型记忆。哪些工作已经完成，哪些任务仍在等待，哪个外部操作处于不确定状态，都需要由代码和持久化状态明确记录。

界面也不再是 Agent 工作发生的地方。网页可以关闭，手机可以稍后接入，进程可以重新启动，但任务本身应该有独立、可检查的生命周期。

这或许就是 Agent Harness 接下来最值得关注的变化：评价一个 Agent 应用，不能只看它最后回答了什么，还要看它能不能说清楚，什么已经完成，什么仍在进行，以及下一步是否安全。

Pi Durable 仍处于实验阶段，但它提出的这些问题，不会只属于一个框架。
