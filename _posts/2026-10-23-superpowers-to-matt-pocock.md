我曾用 Superpowers 组织开发，它把需求讨论、设计、计划、实现和验证串成了一条完整流程。但项目变大后我逐渐发现，再完整的任务流程，也不能替 Agent 回答“这个能力归哪个模块、应该从哪个接口进入”。这是促使我调整开发方式的第一个原因。

## Superpowers 的流程僵化

切换还有一个很现实的原因：完整流程用在复杂任务上很有帮助，用在已经明确的文案或机械修改上，准备工作却可能比修改本身还重。每次都从需求讨论、设计和计划重新起步，会让小任务花很多时间证明自己足够简单。

我现在希望先看任务的行为和风险。小而明确的修改，记录范围后直接实施和验证；涉及权限、数据一致性或跨模块接口的改动，再进入需求确认、设计和更严格的审查。Matt Pocock Skills 可以按当前问题选用：需求不清时澄清，故障难定位时诊断，范围确认后再实施，不适用的环节不必为了走流程而启动。

这里没有做两套工具在相同任务上的耗时或 token 对照。我看重的是减少重复准备和交接时的反复解释，把精力留给真正影响设计与交付的决定。

## 越来越重要的软件设计思路

我现在更看重《软件设计的哲学》强调的深模块：把一项能力收进清晰的边界里，对外只露出尽量小的接口。接手任务的人不必先读遍内部实现，才知道从哪里下手。

在这个项目的后端，每个纳入这套规则的业务模块都以 `api.py` 作为唯一的跨模块入口，并显式声明模块依赖。架构检查会拦住跨模块的内部引用和依赖环。Agent 要修改一项能力时，先定位模块和接口；需要理解内部细节时，再沿着这个入口往里读。

这也是我保留严格设计与交付要求的原因。涉及权限、数据一致性或跨模块接口的任务，要先在 Issue 中写明模块职责、公开接口、关键不变量和测试边界，实施完成后再核对代码是否遵守了这些决定。规则的目的很具体：让项目变大之后，下一次检索仍有可靠的入口，而不是每次都让 Agent 重新猜一遍代码结构。

## 解决 Spec 与 Issue 之间的鸿沟

第二个问题发生在任务交接时。讨论和 Spec 里可能比较过几种方案，到了 Issue，内容往往被压缩成“要做什么”和验收条件。接手的人知道该实现什么，却未必知道当初为什么排除了另一种做法，同样的问题就会被反复讨论，甚至做出相反的决定。

这也是 Matt Pocock Skills 吸引我的地方。`/grill-with-docs` 在澄清需求时整理项目术语，并把值得长期保存的架构取舍写进 ADR；`/to-spec` 则把已经确认的任务内容交给 Issue。它们管的是不同层面的信息：Issue 跟着当次任务走，ADR 让后续任务也能查到重要决定的背景。

![Issue 与 ADR 分别承接任务和长期决策](/assets/images/15-superpowers-to-matt-pocock/02-issue-adr.png)

*图 2：Issue 承接当次任务，ADR 为后续任务保留关键理由。依据 [Matt Pocock Skills 官方说明](https://github.com/mattpocock/skills)与本文的项目实践绘制。*

模块边界就是一个例子。项目的 ADR 记录了为什么选择 `api.py` 作为唯一的跨模块接口、为什么用自动检查约束依赖，也记录了为什么没有选择“每个模块写一份设计文档”。几个月后再碰到跨模块调用，Agent 看到的不只是一条规则，还有规则背后的取舍。

当然，不是每个任务细节都值得写成 ADR。一次任务的具体设计留在 Issue；只有难以逆转、容易让后来者困惑的架构决定，才进入 ADR。这样既保留了理由，也不会让决策文件变成另一堆难以检索的任务日志。

## 我想换的是工作的重心

[Justin Yan 写自己从 Superpowers 切到 Matt Pocock Skills](https://justinyan.me/post/6676)，谈到按需调用 Skill、减少流程负担。这也是我切换的重要原因。在最近的开发中，我还想解决两个会不断累积的问题：**让代码有明确入口，让决定有长期出处。**

Matt Pocock Skills 让我按任务选用步骤，也给了我澄清需求、沉淀领域知识和架构决策的工具；项目自己的规则继续约束复杂任务的设计、实现和审查。下次 Agent 接手任务，它可以从接口找到代码，从 Issue 找到本次任务的边界，从 ADR 找到过去的理由。简单任务少一些准备，复杂任务仍有清楚的依据。
