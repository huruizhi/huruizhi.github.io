这是一份横向扩展 Gitaly 的架构提案：通过以对象存储作为事实来源，将计算与存储解耦，并为 Git 引入自定义的 MVCC 后端。

## 概要

Gitaly 将仓库的权威副本保存在提供服务的节点文件系统中。因此，计算与存储紧密耦合，很难单独扩展其中任意一个维度。

这份蓝图提出一种新架构，将计算与存储解耦，使两层能够独立扩展：

- **存储**：对象存储（例如 AWS S3、Google Cloud Storage、SeaweedFS）是仓库数据的唯一事实来源。
- **计算**：无状态 Gitaly 节点针对从对象存储获取并保存在本地缓存中的制品执行 Git 操作。

这一方案的基础，是我们一直在向 Git 上游贡献的可插拔对象数据库基础设施。有了这层基础，我们便能掌控引用数据库与对象数据库的格式，并创建一套专门满足 Gitaly 特殊需求的存储格式。

在此基础上，我们提出用于存储引用和对象的新型多版本并发控制（MVCC）后端。仓库的持久状态由一组不可变、按内容寻址的制品组成。一份不可变清单指出当前应当启用哪些制品。当前生效清单由仓库的当前代际命名。该设计能够提供一致性读取与原子更新，而且在同一仓库中运行的多个 Git 进程可以分别操作它的不同版本。

Gitaly 是整个流程的编排器：它把生效清单中列出的制品拉取到本地磁盘，针对这份缓存运行 Git，再将新制品发布回对象存储，最后通过有条件地创建下一代对象来激活新清单。

由于对象存储保存权威状态，任何节点在完成缓存填充后都能为任何仓库提供服务；节点也可以按需增加或销毁，而不会造成数据丢失。本地磁盘实际上只充当缓存。Gitaly 节点前面还有一层编排层，负责按需扩缩容集群并高效路由请求。

## 动机

目前，一个仓库的工作负载被绑定在单个节点上：仓库位于某个节点的文件系统中，所有针对它的请求也都由该节点处理。要承载某个仓库的更多负载，唯一办法就是升级节点硬件。但纵向扩展存在上限，而我们的一些大型节点已经触及这个上限。

因此，我们所提供的一些资源消耗最高的 RPC，会直接决定单个仓库能够承载多少流量：

- 为 `gitlab-org/gitlab` 执行一次克隆时，`git-pack-objects` 会占用约 4～6 GB 匿名内存；无论 CPU 是否还有余量，这都会限制单节点可同时处理的克隆数量。
- 对于热门仓库，epoll 竞争、文件描述符耗尽和 CPU 消耗经常成为系统瓶颈。
- Slowloris 风格的客户端会缓慢读取响应，同时持续占用 `git-pack-objects` 的内存。
- 大量 CI 任务同时抓取同一个仓库，经常会把 Gitaly 压垮。

除此之外，我们还观察到由智能体工作负载引起的 RPC 调用显著增加，并预计这种增长会继续加速。如果不能按仓库横向扩展，最繁忙的仓库终将超出任何单节点的服务能力。

因此，我们必须能够在一组节点组成的集群中横向扩展单个仓库的工作负载。我们曾尝试通过 Praefect 的读取分发解决这个问题，但由于多方面原因，这项工作基本未能形成真正可以横向扩展的集群。

### 目标

- 对象存储是仓库数据的唯一事实来源。
- Gitaly 节点是无状态的：丢失一个节点及其磁盘只会导致性能下降，也就是缓存变冷，但不会导致数据丢失或服务不可用。
- 单个仓库的读取负载可以在多个节点之间横向扩展。
- 读取看到的是一致的、某个时间点的快照。
- 写入发布是原子且隔离的，通过有条件、仅允许创建的方式写入下一代对象来完成串行化。
- 本地工作集的开销保持较小：节点只获取给定仓库所需的制品，并清理不再被引用的旧数据。

### 假设

- 大多数仓库以读取为主；扩展读取比扩展写入更迫切。因此，我们首先关注读取扩展。不过，这套设计同时允许多个读取者和多个写入者，我们预计它也能推动写入吞吐瓶颈继续向后移动。
- 为获得更高吞吐量，可以接受每个请求增加一定延迟。缓存与感知缓存状态的路由会尽量降低这部分额外延迟。
- 对象存储提供原子的单键写入、写后读一致性以及条件写入。

## 提案

该架构把持久存储层与无状态计算层分开，并在客户端与节点之间放置一层路由。

![Gitaly 将无状态计算与对象存储中的权威数据解耦](/assets/images/gitlab-git-scaling-design/01-architecture.png)

各组件承担以下职责：

- **对象存储**是仓库数据的唯一事实来源。对于每个仓库，它保存一组不可变、按内容寻址的制品（清单正文、packfile、reftable、索引），以及一个 `generations/` 前缀。该前缀提供曾经生效过的清单的有序序列，并标明当前生效的清单。指针只能通过原子的比较并交换操作向前推进。
- **Git**提供 MVCC 引用后端和对象后端。它本身不执行任何网络 I/O：只读写本地文件，而它能够看到哪些文件则由生效清单决定。把某个 Git 进程固定到特定清单，就能得到一致的时间点快照。
- **Gitaly**是在每个计算节点上运行的无状态编排器。对于每次 RPC，它解析清单指针，把清单列出的制品预取到本地缓存，启动固定在该快照上的 Git，上传所有新产生的制品，并通过推进指针来发布写入。本地磁盘只充当缓存，因此节点不保存任何权威状态，可以被销毁而不会丢失数据。
- **路由器**位于节点前面，把每个请求映射到某个节点，并优先选择已经为目标仓库保有热缓存的节点。它还会根据负载对集群进行扩缩容。

## 设计与实现细节

### Git MVCC 后端

新存储架构的基础，是一套为引用和对象量身定制的存储后端。该后端具有以下特征：

- 支持一致性读取。
- 允许多个读取者读取仓库的不同版本。
- 支持原子写入。
- 能清晰标识读取仓库任意给定快照时所需的全部文件。
- 完全自描述，因此仅凭清单就能在没有额外信息的情况下引导出一个完整的 Git 仓库。
- 所有数据均按内容寻址，因此两个并发写入者不会彼此冲突。

这些特征结合起来，使我们能够仅凭一份清单文件组装出完整仓库。编排器因而可以把权威状态保存在对象存储中，只把服务某个特定仓库版本所需的文件拉入本地缓存，也只上传生成另一个特定版本所需的文件。

#### 目录布局

所有制品都位于同一个缓存目录下。除了唯一可变的 `manifest` 指针外，其余内容都不可变并按内容寻址：

```text
<commondir>/mvcc/
  manifest               可变指针（生效清单的哈希）
  manifests/<hash>       不可变的清单正文
  pack/<hash>.pack       不可变的 pack
  pack/<hash>.idx
  pack/<hash>.rev
  refs/<hash>.ref        不可变的 reftable
```

由于除指针外的所有内容都按内容寻址，新文件可以安全地与现有文件并存：两个生成同一制品的写入者不会发生碰撞；中止的写入留下的文件也只是暂时无人引用，在被回收之前不会造成危害。

#### 清单格式

清单正文是建立在 [`gitformat-chunk`](https://git-scm.com/docs/gitformat-chunk) 框架之上的分块二进制文件，用于枚举某一个一致快照所包含的制品。文件头包含 `MVCC` 签名、格式版本、块数量、`PATH` 记录的定长尺寸，以及仓库所采用的对象哈希算法（SHA-1 或 SHA-256）。随后包含三个块：

- `PATH` 是按字典序排列的定长、以 NUL 结尾的相对路径列表（相对于缓存目录）。这是编排器获取和上传制品时使用的规范制品列表。
- `OBJS` 是一个指向 `PATH` 的 `(start_index, count)` 范围，用于指定对象存储制品。
- `REFS` 是按 reftable 栈顺序排列的 `PATH` 索引序列；对于同一个引用，较后的表会遮蔽较早的表。

正文末尾有一个 32 字节的 SHA-256，它既用于在解析时检测损坏，也作为正文的内容寻址名称。只需要枚举任意快照依赖项的消费者，只需读取 `PATH` 块。未知的块 ID 会被忽略，因此未来可以加入新的制品类型，而无需提升格式版本或修改 Gitaly。

#### 固定版本与指针解析

Git 按照固定优先级解析生效清单：

1. `GIT_MVCC_MANIFEST` 环境变量允许调用方把 Git 固定到某个具体清单版本。这会得到一个只读快照；Git 在尝试写入任何制品时都会中止。
2. `GIT_MVCC_MANIFEST_PATH` 环境变量允许调用方指示 Git 从给定路径读取并更新清单。
3. 如果上述覆盖项都未启用，则使用仓库自身的 `<commondir>/mvcc/manifest` 指针。

设置 `GIT_MVCC_MANIFEST=<sha>` 会在读取时覆盖磁盘上的所有指针，并在整个进程生命周期内使该句柄保持只读。任何进程都通过这种方式获得一致的时间点视图。

可以通过导出 `GIT_MVCC_MANIFEST_PATH` 并使用多个不同的临时清单来隔离写入。这个环境变量会指示 Git 使用临时清单，将它作为当前清单版本的事实来源，并在写入新数据时把新清单版本发布到该路径。这样，Gitaly 就能隔离多个写入者，使尚未发布的状态不会被其他正在进行的进程看到。

由 Git 执行的钩子会继承 `GIT_MVCC_MANIFEST` 环境变量，从而看到与父进程相同的清单版本。这也能确保子进程无法写入数据。

需要注意的是，当规范的事实来源最终位于对象存储中之后，Gitaly 将不再使用 `<commondir>/mvcc/manifest`。它应当始终从对象存储中的仓库当前代际解析版本，然后通过 `GIT_MVCC_MANIFEST` 导出该版本，或者把版本写入 `GIT_MVCC_MANIFEST_PATH`。

如果既没有设置 `GIT_MVCC_MANIFEST`，也没有设置 `GIT_MVCC_MANIFEST_PATH`，Git 就使用 `<commondir>/mvcc/manifest` 中的指针。

#### 范围

该后端本身不执行任何网络 I/O：生效清单中列出的每个对象都必须已经存在于本地；缺少制品属于硬错误，而不是触发拉取操作。与对象存储的全部通信都由接下来介绍的编排器负责。

### 以对象存储作为事实来源

对于每个仓库，对象存储会保存完整的制品集合，以及一个持久的 `generations/` 前缀。该前缀提供曾经生效过的清单的有序序列，当前清单则是按字典序排列在最前面的那个。Gitaly 会在每次 RPC 开始时解析当前代际，绝不会把本地缓存指针当作权威信息。

每一代都以独立键的形式保存在 `generations/` 前缀下：

```text
<repository>/
  generations/<generation>          内容：生效清单的哈希
  generations/<generation>.<hash>   优化：把清单哈希放入键名
  manifests/<hash>                  不可变的清单正文
  ...
```

代际编号是一个从 `UINT64_MAX` 开始递减计数、以零填充的十六进制数。因此，当前代际始终拥有按字典序最小的键，调用 `List(prefix="generations/", limit=1)` 时，返回结果中的第一个键就是当前代际。代际对象的内容是该代际生效清单的哈希。

激活新清单时，系统先解析当前代际，然后以有条件、仅允许创建的方式写入下一代对象。如果键已经存在，写入就会失败。出现这种情况，说明并发写入者已经创建了这一代。后面的写入 RPC 生命周期会说明如何处理该冲突。

为了避免额外读取，还可以创建 `generations/<generation>.<hash>` 形式的辅助键，把清单哈希直接编码进键名。这样，当该键已经可见时，Gitaly 无需读取代际对象正文就能知道清单哈希。

如果代际编号有一天发生下溢，该方案会进行回卷：新纪元的键会添加一个保留前缀字符，该字符在字典序上排在所有十六进制数字之前；此后每次再次回卷，都会再添加一个这样的字符。因此，新纪元的键仍会排在最前面。

> **重要说明**
>
> 该设计的早期版本使用单个可变的清单指针键，并通过比较并交换来推进它。后来放弃了这种做法，因为对象存储提供商会限制对同一个键的更新频率。例如，Google Cloud Storage 每个对象每秒只允许更新一次。

对象存储提供商需要满足以下要求：

- 支持具有写后读一致性的单键 PUT。
- 支持对代际对象执行有条件、仅允许创建的 PUT。
- 支持按前缀、字典序和数量限制列出键。
- 支持条件删除，以保证后台维护安全。
- 支持更新对象的 ETag。

编排器负责在启动 Git 之前获取已解析清单的全部依赖项。与此同时，编排器也负责上传即将激活的新清单所需的全部依赖项。

### 读取 RPC 生命周期

`GetCommit` 或 `FindRefs` 等读取 RPC 需要一个一致快照，但不会产生新状态。

![读取 RPC 解析清单并预取缺失制品的生命周期](/assets/images/gitlab-git-scaling-design/02-read-rpc.png)

Gitaly 通过一次 `List(limit=2)` 调用解析当前代际：如果带哈希后缀的键已经可见，便可以直接从键名得出清单哈希；否则，Gitaly 会回退为读取代际对象本身。

Gitaly 只需通过 `PATH` 块枚举 MVCC 快照所需的依赖项，不必解释其他任何块。由于制品不可变且按内容寻址，预取操作具有幂等性。通过 `GIT_MVCC_MANIFEST` 固定版本，可以确保一次 RPC 中启动的每个 Git 进程都观察到相同状态，即使其他写入者正在推进仓库版本也不受影响。系统不会创建外部指针文件，读取也永远不会推进缓存指针。

> **重要说明**
>
> 对于任意一次 RPC 调用，必须只把当前代际解析为一个具体清单版本一次；所有 Git 进程都必须继承这个完全相同的版本，避免在并发写入时观察到撕裂读取。

如果缓存尚未预热，获取缺失制品可能会花费很长时间。系统将通过两种机制缓解这个问题：

- 路由层需要确保请求被路由到拥有热缓存的节点。
- 仓库后台维护需要避免不必要地重写制品，从而限制变更数据量的上界。

### 写入 RPC 生命周期

`UserCommitFiles` 或 `PostReceivePack` 等写入 RPC 会产生必须持久化的新状态。

![写入 RPC 上传新制品并条件创建下一代对象的生命周期](/assets/images/gitlab-git-scaling-design/03-write-rpc.png)

Gitaly 首先会按照处理只读 RPC 时的相同方式解析清单。不过，它不会通过 `GIT_MVCC_MANIFEST` 固定版本，而是把解析出的清单版本写入一个临时清单路径，并使用 `GIT_MVCC_MANIFEST_PATH` 调用 Git。这样，所有更新都被包含在自己的临时状态中，不会影响并发写入。

Git 完成后，Gitaly 可能需要检查新状态。检查的一部分可能是调用 Rails 的 `/internal/allowed` 校验，而这些校验会针对新状态执行一组读取。为了让这些读取可以分布到不同节点，Gitaly 必须在写入下一代对象之前就把制品上传到对象存储。此后针对该版本的校验，应当传递指向提议新版本的 `GIT_MVCC_MANIFEST`。

这里存在一个取舍：

- 访问检查本身可能成本很高，因此把它们分布到多个节点可以提高潜在吞吐量。
- 分布式读取必然要求其他节点获取新制品。

我们可能会希望在访问检查期间限制读取分发，把后续读取固定在执行写入的节点上。

> **重要说明**
>
> 与只读 RPC 相同，清单版本必须只解析一次。从此以后，在这个变更型 RPC 中，临时清单应当成为所有后续 Git 进程所使用的清单版本的唯一事实来源。
>
> 此外，下一代对象必须**至多写入一次**，否则变更型 RPC 可能造成撕裂写入。

新状态被接受并且制品完成上传后，Gitaly 会以有条件、仅允许创建的方式写入下一代对象。因为可能同时存在多个写入者，该操作可能失败：另一个并发写入者已经创建了这一代。此时存在两种情况：

- 可能存在逻辑冲突，例如同一个引用被更新为不同版本。此时应拒绝操作，不发生任何更新。
- 也可能只在操作层面存在冲突：当前代际已经推进，但各项更新本身并不冲突。此时，Gitaly 会对发生变化的引用执行三方合并，尝试解决冲突。

三方合并会使用三个相关清单：

- **Base**：Gitaly 最初写入临时清单指针的版本。
- **Ours**：变更型 RPC 计算出的提议更新；所有执行写入的 Git 命令结束后，可以通过读取临时清单指针得到它。
- **Theirs**：当前代际所指定、已被并发写入者推进的版本。

合并过程会读取这三个版本之间发生变化的引用并进行合并。如果任何引用收到了相互冲突的更新，就属于逻辑冲突，应拒绝写入。反之，如果没有引用收到多次写入，就可以接受合并结果，并针对新的当前代际重试条件写入。

对象不需要三方合并。可以把对象视为无冲突数据，始终取它们的并集。

### 仓库后台维护

这套设计会在每次写入时产生新的 packfile 和 reftable。为了限制单个清单引用的文件数量、保证快速查找数据，并为对象增量压缩创造良好条件，我们必须定期执行压缩整理。

压缩整理需要平衡两个目标：

- 我们希望文件数量尽可能少，以保持快速查找。
- 我们希望避免频繁重写文件，减少其他节点上的缓存未命中。

系统通过带有 packfile 最大尺寸的几何压缩来平衡这两个目标。小于给定阈值的全部文件，在尺寸上必须形成几何级数。如果不满足这个条件，就尽可能重新打包多个文件以恢复该性质。一旦文件达到尺寸阈值，系统便不再重新打包它。

冻结的 packfile 还保证了一项重要性质。假设仓库缓存已经用清单 A 预热，而我们使用比 A 更旧的清单 B 执行快照读取，那么可以确定：

- B 中存在的任何冻结 pack 也存在于 A 中。
- 所有未冻结 pack 都构成一个几何级数。
- 这个几何级数的总尺寸最多为 $\frac{T r}{r - 1}$，其中 $T$ 是阈值，$r$ 是几何级数的比率。

通过调整这些参数，我们便能限制必须获取的数据量上界。当阈值为 1 GB、比率为 2 时，需要获取的数据量上界为 2 GB。

需要注意，这里假设系统默认不再删除不可达对象。对于大多数仓库，这预计是可以接受的。

### 垃圾回收

MVCC 后端会在每次修改时创建新制品。因此，未被引用的制品会随着时间推移在本地磁盘和对象存储中不断累积。为了控制存储增长，我们必须定期清理这两个位置。

节点上的数据只用作缓存，因此可以安全地积极执行本地清理。对象存储的清理逻辑则必须以不会和并发读取者、写入者产生竞态的方式实现。

该系统中有两种垃圾回收：

- 清理旧清单应当可以配置。这样便能根据特定策略，在一段时间内保留多个时间点恢复版本。
- 清理未引用制品则不必由策略控制。

下面只讨论如何无竞态地删除未引用制品。为此，系统使用两代删除队列。

![使用两代删除队列进行无竞态垃圾回收](/assets/images/gitlab-git-scaling-design/04-garbage-collection.png)

当某个节点决定执行清理时，它会扫描所有可用的清单文件并列出所有现存制品。清理候选集的计算方式，是从现存制品列表中移除被任意清单引用的制品。除此之外，还要检查每个制品的 mtime 是否早于“当前时间减去给定阈值”。计算结果就是符合清理条件的候选集。

节点随后根据候选集创建新的删除队列。该队列包含：

- 应当删除的制品名称。
- 每个制品的 ETag，用于执行条件删除。

节点下载当前删除队列，并通过比较并交换操作将它更新为新的候选列表。如果更新成功，节点便检查下载队列中待删除的列表。对于每个条目，它使用删除队列中保存的 ETag 执行该制品的条件删除。

如果写入者开始引用一个先前未被其清单引用、但已经存在于对象存储中的制品，那么它必须更新该对象在对象存储中的 ETag。这样，当没有其他清单引用该制品时，清理任务也不能并发删除它。如果 ETag 更新因为并发删除而失败，写入者就必须重新上传该制品。

后台维护任务无论在交换操作之前、期间还是之后崩溃，都不会造成问题，因为未来的再次执行会重新推导应当清理的候选集。

### 去重网络

派生仓库时，系统会创建一个新仓库，它起初是上游仓库的完全相同副本。即使派生仓库后来与上游分化，二者通常仍然共享一段共同的基础历史。既然知道这种关系，就应当对派生仓库和上游仓库中同时存在的对象进行去重，以降低总体存储占用。对于智能体工作负载中常见的大量派生式工作流，这一点尤其重要。

在当前架构中，Gitaly 通过对象池仓库实现对象去重。对象池是一个独立的 Git 仓库，其中包含准备与其他相关仓库共享的一组对象。依赖这些共享对象的仓库，通过 Git alternates 机制链接到对象池。

在 MVCC 设计中，每个 Git 仓库都有一个当前代际，用来定义正在使用的 MVCC 制品，也就是 reftable、packfile 和清单。由仓库当前代际指定的清单，实际上允许 Git 构建该仓库的隔离快照或视图。把拥有相关历史的仓库关联起来，例如上游与它的派生仓库，就可以通过共享 MVCC 制品池实现制品去重。这是因为 MVCC 制品按内容寻址且不可变。共享同一个 MVCC 制品池的一组仓库，被称为一个去重网络。

![多个仓库通过共享 MVCC 制品池组成去重网络](/assets/images/gitlab-git-scaling-design/05-deduplication-network.png)

创建一个全新仓库时，会把该仓库放入新的去重网络；创建派生仓库时，则让它加入现有去重网络。为了实现这一点，每个仓库需要知道自己从哪个 MVCC 制品池获取数据，以及自己的 `generations/` 前缀。这些信息可以保存为仓库键与制品池/代际位置之间的键值映射。在集群环境中，使用同一制品池的仓库最好被路由到同一个 Gitaly 节点，以便在本地缓存中实现制品去重并减少冷缓存命中。

要让制品级去重生效，制品必须在某个时点之后保持稳定。例如，仓库后台维护可能为了让 MVCC 制品更紧凑而重写它们，结果会产生新的、彼此不同的制品，不再被去重网络中的多个仓库共同使用。对于 packfile 制品，可以通过设置尺寸上限来阻止重新打包。这样，“大型” packfile 便能在仓库写入过程中保持不变，并被去重网络中的仓库重复使用。这也意味着，随着仓库历史继续演化，小于尺寸上限的 packfile 制品不太可能继续保持去重。此外，可以去重的 packfile 制品集合在派生仓库创建时就已经确定。

需要注意，reftable 和清单制品理论上也可以去重，因为它们同样位于共享池中。但在实践中，随着仓库历史演化，这些制品不太可能保持稳定，因此通常不会被去重网络中的多个仓库共同使用。

### 集群与路由

Gitaly 节点必须以集群方式运行，才能实现横向扩展。集群与路由层负责让节点知道彼此的存在，并根据一组条件把请求路由到健康节点。该层应当与部署环境无关，也就是说，无论在 Kubernetes 内部还是外部都应正常工作。

尽管节点只是无状态缓存，理论上可以为任意仓库处理请求，但这样做并不理想，原因如下：

- 如果目标节点此前没有服务过某个仓库，就需要预热缓存，也就是从持久存储下载缺失的制品，这会带来额外开销。
- 本地磁盘占用会很高，因为每个节点在其生命周期内都有同等机会服务所有仓库。

因此，路由器的首要目标，是确保对给定仓库的请求“粘滞”在集群中的一小组节点上。例如，`repo-a` 的请求应始终被导向 `gitaly-1` 和 `gitaly-4`，让这两个节点都能保持相对热的缓存。

路由器背后由集群层提供支持。集群层维护集群组成及各个节点的健康状态，也允许在无需重新配置现有节点的情况下调整集群规模。

关于提议实现的更多信息，请参阅子页面 [Clustering and Routing](https://handbook.gitlab.com/handbook/engineering/architecture/design-documents/scaling-git/clustering_routing/)。

## 迁移

完整落地整个项目将是一项大工程。为了尽快验证系统的不同特征，我们会把项目拆分成多个阶段：

1. MVCC 引用迁移
2. MVCC 对象迁移
3. 对象存储迁移
4. 集群化

每个阶段只推出整体设计中的一小部分，而且大多数阶段已经能够为客户提供价值。这样可以缩短进入生产环境的时间，尽早暴露设计问题，从而降低整个项目失败的风险。

### 阶段 1：MVCC 引用迁移

第一阶段只推出针对引用的 MVCC 后端。这需要 Git 中的 MVCC 引用后端，以及 Gitaly 侧处理读取和写入的逻辑。

把这个阶段与对象迁移分开的好处是：引用后端在 Git 中已经完全可插拔，而且我们已经有一条迁移路径。因此，在可插拔对象数据库的基础设施仍处于收尾阶段时，就能先推出这一部分，并开始验证 Gitaly 对 MVCC 逻辑的处理。

这一阶段还会把 Git 引用的存储后端迁移到 reftable，从而解决删除引用时长期存在的扩展性问题。除此之外，它给客户带来的直接收益比较有限。因此，我们预计只会在预发布环境中的仓库以及少量面向生产的仓库中推出这一阶段。

### 阶段 2：MVCC 对象迁移

第二阶段会推出对象的 MVCC 后端，使引用和对象都由 MVCC 支撑。这要求可插拔对象接口能够满足 Gitaly 的需求，也需要 Git 中的 MVCC 对象后端。Gitaly 侧处理读取和写入的逻辑已经在第一阶段实现。

完成这个阶段后，仓库将具备对象存储所需的准确布局，但全部数据仍然位于本地磁盘。至此，Git 侧所需的全部改动都已完成。

该阶段提供以下收益：

- 所有读取都完全一致，不会受到并发写入者影响。
- 写入具有原子性。
- 可以在指定时间点执行快照读取。

这一阶段是平滑迁移到对象存储的前提。因此，我们预计最终会把所有仓库迁移到这个后端。

此外，对于非企业客户，这也将是最后一个阶段。

### 阶段 3：对象存储迁移

第三阶段会把仓库数据的事实来源从本地磁盘迁移到对象存储。实质上，这意味着每个仓库一开始都由一个只包含单个 Gitaly 节点的集群承载。

该阶段提供以下收益：

- 可以通过对象存储执行全局一致的备份。
- 可以开始从本地磁盘清理仓库数据，从而降低存储成本。
- 因为唯一事实来源位于对象存储，任意 Gitaly 节点都可以轻松服务任意仓库。

预计 GitLab.com 的全部仓库都会迁移到这个阶段。该迁移只面向企业客户执行。

### 阶段 4：集群化

第四阶段会在 Gitaly 中引入集群管理能力，包括智能路由，以及根据负载自动扩大或缩小集群规模。

该阶段提供以下收益：

- 可以根据某个特定仓库的负载动态扩容或缩容。

## 备选方案

### Praefect

Praefect 已经提供读取分发。但在实践中，Praefect 被证明很难运维：

- 使用 PostgreSQL 会形成多个事实来源，备份起来很有挑战。
- 事务投票机制在实践中被证明不可靠。
- 写入必须同时发生在所有节点上。因此，为某个特定仓库提供服务的节点越多，其中一部分节点失败的概率就越高。
- 故障模式经常导致复制任务永远无法追上并发写入。结果是读取分发失效。

因此，这个方案被视为一个失败的设计。

### 网络文件系统

在使用 Praefect 之前，我们使用网络文件系统在多个 Gitaly 节点之间分发数据。但更高的访问延迟被证明是一个难题。此外，网络文件系统往往会出现不符合 POSIX 的边缘情况，导致问题难以调试。

### 把 Git 数据存入数据库

另一个曾被考虑的方案，是把 Git 引用和对象存入真正的数据库。这样做的好处是，任何客户端都可以轻松访问这些数据。

然而，Git 的许多操作要求读取完整对象图和全部引用。考虑到网络往返时间，如果逐个读取这些数据，实际系统将无法工作。

一种可能的前进方向是引入多层重度缓存。但由于整个项目的时间要求非常紧迫，而且这条路线存在太多未知因素，目前已暂时放弃该方案。

## 风险与开放问题

新系统同样存在自身的风险：

- 用额外延迟换取吞吐量的取舍，在某些场景中可能无法接受。一种可能的缓解方法，是在一定时间内缓存已经解析的代际。
- 对于包含大量文件或大型文件的仓库，冷缓存填充延迟值得担忧。一种可能的缓解方法，是主动预热缓存。
- 压缩整理的频率和粒度必须与缓存失效成本保持平衡。
- 对对象存储的读写限流可能形成瓶颈。

这些风险需要通过早期基准测试来解决。
