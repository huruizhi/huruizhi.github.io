Matt Pocock 是一位专注 TypeScript、AI 编程和开发者工作流的技术作者与教育者。他维护的 skills 仓库最近发布了 v1.3，带来了几项面向 Agent 编程协作的更新。

我最近重新看了其中三个 Skill，`/implement-spec`、`/pr` 和 `/retro`。

它们刚好对应 Agent 工作的三个阶段：更好的规划任务，将结果显示成人类更好阅读的格式，完成后检查这次过程哪里可以变得更好。

## /implement-spec：先画任务图，再动手

`/implement-spec` 适合处理一份相对完整的 spec。

比如我要给一个项目增加权限控制，这件事通常不会只改一个接口。数据结构、服务端逻辑、前端状态、测试和文档，可能都要动，而且彼此有先后关系。

过去我可能会开一个会话，从第一个文件一路改到最后一个文件。中间遇到别的问题，就顺手处理一下。等 Agent 终于说完成了，我知道它改了很多东西，却未必说得清这些改动之间是什么关系。

`/implement-spec` 的思路是先把 spec 和 ticket 读一遍，再把任务之间的依赖整理成一张图。

这很关键。任务之间有阻塞关系，已经准备好的任务可以同时开始，必须等待前置任务完成的部分就先停在那里。

每个实现任务交给一个独立的 sub-agent，在自己的 worktree 里完成。实现时仍按测试驱动的方式验证，做完以后把分支合回同一个 integration branch，最后统一 review 和收尾。

这里最值得借鉴的是工作边界被划清楚了，并行只是这种安排带来的结果。

一个 sub-agent 只需要拿到和当前 ticket 相关的上下文，就能开始工作。它交出来的是一个可以被合并、被检查的分支，改动不会散落在某个会话里的几段代码中。

对复杂需求来说，这种方式让 Agent 更接近一个小型开发团队，工作边界也更清楚。

当然，前提是 spec 得足够清楚。目标、边界、验收条件都没写明白，任务图画得再漂亮，也只是把一个大模糊问题拆成一堆小模糊问题。

## /pr：交付要把证据摆到桌面上

`/pr` 处理的是如何把已经完成的工作交到审查者面前。

我以前看 Agent 生成的 PR 描述，经常是一大段改动摘要。文件列了不少，测试命令也列了不少，但看完以后我还要自己判断三件事：这次到底改了什么，关键行为有没有验证，合并以后出了问题能不能退回来。

`/pr` 把这件事压缩成三个部分。

**Summary** 负责让我快速看懂改动的形状。它可以是一棵文件树、一段调用关系，或者一张足够小的图。PR 不需要写成长文，先让我在打开完整 diff 之前看懂这次改动的主要路径。

**Evidence** 负责回答「功能是否真正生效」。

证据可以是测试结果，也可以是修改前后的行为对比。有界面的功能，截图比一句"测试通过"更有用；接口变化，请求和响应的差异比一串文件名更有用。

**Merge Danger** 则把风险摊开：哪些模块会受影响，哪些动作合并后不容易撤回，出了问题回滚的范围有多大。

三部分里，Evidence 最容易被忽略，也最实用。

Agent 很擅长生成看起来完整的代码。它可以告诉我改了什么，也可以告诉我测试跑过了。但需求里最关键的那个行为，可能从来没有被真正验证。

没有证据时，我只能凭感觉审查。而一大段完整的代码，恰好最容易让人放松警惕。

所以我现在更愿意把 PR 看成一次交付说明：它既要说明代码改动，也要把完成情况、验证过程和剩下的风险说清楚。

## /retro：结果对了，不代表过程没浪费

代码写完以后，还有一个问题经常被漏掉：这次工作为什么这么慢，Agent 在哪里迷路了，下次能不能少走几步弯路。

这就是 `/retro` 的用武之地。

它会重新检查一次真实的 coding 会话：代码导航是否顺畅，项目里有没有缺少自动化检查，编码规范是否容易找到，工具调用有没有反复消耗时间，还有那些写进全局约定却没有实际生效的指令。

这些问题通常不会出现在最终 diff 里。

代码可能是对的，功能也能用，但 Agent 可能在几个目录之间来回找，重复读取同一份文件，或者一直没找到项目里最重要的约定。只看最终结果，这些过程里的浪费就被遮住了。

`/retro` 的价值，就是把这些摩擦重新捞出来。

它甚至能发现一些和代码没有直接关系的工程问题：一次发布记录里跳过了应该存在的版本，某个重要检查流程只写在人的记忆里，没有落到仓库约定中。

但这里一定要保留人的判断。

retro 可以提建议，不能替我决定仓库以后该怎么工作。它发现的困难可能只是一次偶然，也可能是规则本身写得不清楚。要不要新增检查、修改文档、调整 Agent 的工作方式，还要结合实际情况判断。

## 一个小改名，CONTEXT.md → GLOSSARY.md

这次还有一个看起来很小的变化：`CONTEXT.md` 改名成了 `GLOSSARY.md`。

文件内容不会因为改名就自动变好，但这个名字把用途说得更清楚了：它主要用来解释项目里的术语、领域概念和团队共识，并且有明确的内容边界。

我以前也容易把项目说明写成大杂烩。遇到新规则就追加，遇到临时决定也追加。时间久了，文件越来越长，真正重要的概念反而更难找。

换成 GLOSSARY.md 以后，至少给了团队一个提醒：哪些内容是在解释项目使用的词，哪些内容应该放到别的地方。

这和 Agent 的关系很直接。

Agent 能不能顺利工作，很大程度上取决于它能不能找到正确的信息。一个名字准确、边界清楚的文件，有时候比再加一条 Prompt 更有用。
