大规模托管 Git 仓库简直是一场噩梦。Linus Torvalds 设计第一版“来自地狱的信息管理器”时——这确实是 Git 的标语，[可以查证](https://github.com/git/git/commit/e83c5163316)——心里想的是一个非常具体的使用场景：他自己的场景。他想替代当时用于开发 Linux 内核的分布式版本控制系统 BitKeeper。这个替代品当然也必须是分布式的。内核是一个不同寻常的软件项目：它高度去中心化，众多子系统分别由不同的维护者负责。分布式版本控制系统天然适合这样的工作流。

二十年后，Git 已成为行业标准。但事实是，它的分布式特性带来的阻碍多于优势。普通开源项目并不会采用去中心化的工作流，普通公司更不会。大家享受分布式模型的诸多好处，例如离线工作、延后推送等，但又非常依赖一个中心化托管服务。事实证明，托管 Git 仓库是一件极其困难的事。

## Git 到底难在哪里？

大规模托管 Git 仓库的挑战，根植于 Git 自身的设计：所谓*分布式*版本控制系统，意味着一个仓库的所有实例都是相同的。Git 服务器上的仓库并没有任何特殊之处，开发者笔记本上的仓库同样具备这些特征。乍看之下，这似乎会让 Git 托管变得简单——只需在磁盘上的仓库副本前放一个 HTTP 守护进程，Git 服务器就搭好了。但现实恰恰相反，其中存在许多棘手的可扩展性和可靠性挑战。

在普通 Git 仓库中，代码和元数据，包括文件、提交和树，都会被压缩后存入 *packfile*。这是一种简单的二进制序列化格式，本地机器处理起来很方便，却不适合在服务器上进行大规模管理。packfile 是 Git 存储和 Git 网络传输的基本构件。向仓库推送或从仓库获取数据时，数据都以 packfile 的形式传输。

Git 的设计本来就是这样，但我们完全有理由认为服务器内部不必照搬这一方式。毕竟，你无法控制 Git 客户端——至少不能在不给用户添麻烦、增加大量摩擦的情况下控制它——但在自己的服务器内部，你想怎么做都可以。没有什么强迫你继续使用 packfile，Linus 也不会过来检查。唯一的限制是：所有 Git 操作在网络上收发的仍然必须是 *packfile*。

多年来，尝试大规模托管 Git 仓库的公司逐渐发现，这种基于 *packfile* 的设计严重限制了可用性和扩展性。packfile 是大型二进制文件，Git 必须通过文件系统访问它。把 HTTP 服务器放在磁盘仓库前面的简单方案，扩展上限很低。理想情况下，一个仓库应该同时存在于多块磁盘和多台机器上，这样既能并行执行大量 Git 操作，也能在服务器故障时保持仓库可用。但要如何实现？

大体上有三条路线，复杂度依次增加：分布文件系统、分布 packfile，或者分布 Git 本身。

## 没有 packfile 的 Git

Git 是一个内容寻址的数据存储。Git 仓库里的所有对象，包括 blob、tree、commit 等，都以其内容的 SHA-1 作为键。直觉上，这与分布式键值存储十分契合：键是 SHA-1，值是实际对象，似乎能让仓库存储优雅地横向扩展。但这种方案实际上行不通。

问题在于，Git 仓库的实际结构是一张有向无环图，简称 DAG。你可以通过 SHA 查找任意对象，但即使执行仓库中最简单的操作，也必须逐步遍历这张 DAG。

![从远程键值存储逐步读取 Git DAG 对象](/assets/images/cursor-git-at-any-scale/01-object-store-dag-walk.svg)

如果要列出仓库最近的变更，就必须处理其中的提交。处理一个提交时，你会得到一个指向根目录树的指针；从这棵树中，又会得到指向每个文件和子树的指针；从原始提交中，还会得到指向父提交，也就是历史中前一个提交的指针。关键在于：遍历的每一步里，只有取回前一个对象后，才能知道下一个指针的值。如果每次读取都需要往返访问分布式存储，成本会迅速变得极其高昂。

在对象层面分布 Git 的方案过去已经尝试过很多次，而且常常在规模化阶段失败。最有希望的一次实践来自我以前的导师 Shawn Pearce，当时他在 Google 的版本控制系统团队工作。他的方案是[把对象存储在分布式哈希表中](https://www.eclipse.org/lists/jgit-dev/msg01189.html)。这要归功于 JGit——一个使用 Java 编写的自定义 Git 实现。像任何优秀的老派 Java 库一样，JGit 提供了足够多的接口、工厂和接口工厂，可以抽象普通 Git 仓库的所有细节，包括用 DHT 替换磁盘上的 packfile。系统确实运行起来了，普通 Git 操作的效果也不错；但 Git 协议的限制仍然存在：无论服务器内部如何存储数据，网络传输都必须使用 *packfile*。最终，`git clone` 的性能差到足以让团队彻底放弃这一设计。

## GitHub 与文件系统

Git 开始走出 Linux 内核的小圈子几年后，一家充满闯劲的初创公司在旧金山诞生。GitHub 于 2008 年成立，定位是社交编程平台，并提出了一句非常有先见之明的标语：“Git repository hosting: no longer a pain in the ass.” 我不是在开玩笑，[可以看看当年的页面](https://web.archive.org/web/20080514210148/http://github.com/)。早在 2008 年，人们就已经形成广泛共识：尽管 Git 采用了分布式设计——或者正因为如此——要让它真正易用，仍然需要一种中心化托管方式，而做这件事非常痛苦。GitHub 决心改变这一点。

GitHub 的平台最初是一个 Rails 单体应用，今天在很大程度上仍然如此。最早的版本运行在一台性能不俗的机器上，Ruby 服务器和仓库副本一起放在本地磁盘中。扩展 Rails 应用很容易：部署更多实例即可。但只要涉及 Git，他们很快就会遇到本文反复讨论的问题：Rails 应用需要访问磁盘上的 Git 仓库，那么仓库副本要怎样一起扩展？

早期的 GitHub 系统工程师是一群精打细算的异类，他们尝试了最简单、最可能解决扩展问题的方法。他们的想法是：如果把精力放在分布*文件系统*上，而不是分布 packfile 或 Git 本身，就能保持 Rails 应用不变，把时间花在为不断增长的用户群开发更多功能上，而不是折腾 Git 的奇怪玩法。这个思路非常务实，但没有成功。

团队为 Git 数据尝试过多种分布式文件系统。最明显的方案是使用 NFS，把所有仓库放在一台中心服务器上，但很快就被放弃了。Git 的默认实现对文件系统语义——锁定、撕裂写入、读取、同步等——做了很多假设。这些假设能让 Git 在开发者缓慢的笔记本本地文件系统上获得不错的性能，却完全没有考虑它们在网络文件系统上的表现。结果既慢，又容易出错。

之后，他们还尝试了几种现在回头看颇为可怕的技术，在块级别复制文件系统：短暂部署过 [GFS](https://en.wikipedia.org/wiki/GFS2)，也较长时间使用过基于 [DRBD](https://en.wikipedia.org/wiki/DRBD) 的方案。它们最终都撞上了墙。日常运维糟糕透顶，性能也不足以弥补这种痛苦。归根结底，问题仍然在于磁盘上 *packfile* 的设计。

前面已经看到，Git 的图结构会让网络往返变得昂贵得难以承受。不幸的是，磁盘上的底层数据也遵循类似规律。对象在 DAG 中的位置，与它们在 *packfile* 中的排列方式没有关联。生成 packfile 时最重要的启发式目标是尽量减小体积，因此对象会被随机地放在 pack 中并被压缩；更关键的是，它们很少以完整形态存储。大多数对象都基于同一 packfile 中的另一个对象以 delta 形式保存。读取单个对象时，不但要沿着图数据结构进行多次逻辑跳转，还要在磁盘格式中进行多次物理跳转。

![git log 遍历提交 DAG 时对 packfile 范围进行随机读取](/assets/images/cursor-git-at-any-scale/02-packfile-random-access.svg)

每一次 Git 操作都需要在数 GB 数据中完成这种随机遍历，它与网络文件系统天生不合，无论该系统是在文件级还是块级复制。唯一能避免性能降到爬行速度的方法，是把整个文件缓存到本地。但同一文件系统中存在数十万个仓库时，整体缓存根本不可行。

最终，GitHub 的系统工程师硬着头皮放弃了分布文件系统。他们开始开发 RPC 系统，让仓库驻留在专用文件服务器上，同时修改 Rails 应用，让所有操作都通过远程调用完成。这带来了可观的横向扩展能力，但没有解决可用性问题，也没有改善最繁忙仓库的性能。毕竟，每个仓库仍然只存储在一台机器上。

## Spokes 与一致性

Spokes 最初由 GitHub 在 2013 年前后开发，此后逐渐成为行业标准。大多数 Git 托管服务的架构都采用了 Spokes 思路的某种变体，也就是在应用层复制 Git 仓库。Spokes 多年来运行良好，主要因为它做出了三个后来被证明十分正确的基础选择：

1. 不分布 Git 本身，而是在 packfile 层面工作。
2. 把所有数据存储为本地 NVMe 磁盘上的真实 Git 仓库。
3. 复制 Git 数据，同时让所有副本始终保持一致。

鉴于前面讨论过的 packfile 随机读取模式，要确保所有基础 Git 操作都保持快速，几乎必须把普通 Git 仓库存储在 NVMe 磁盘上。这样也能让 clone 保持高效，因为不必把数据转换成 Git 客户端期待的格式；同时，团队可以专注于在 Git 之上开发产品，而不是维护一个能够处理特殊仓库格式的 Git 分支。

让所有数据副本始终一致同样至关重要。这件事往往要吃过苦头才会明白：Git 客户端与最终一致性真的合不来。如果本地 Git 客户端推送了一个提交，随后 fetch 却无法立即读到它，情况会很糟，Git 会对此十分困惑。如果 CI 流水线运行在一百个 runner 上，其中三个在 clone 后找不到本应测试的提交，同样会出大问题，用户体验也极差。

无论在客户端还是后端，面对最终一致的 Git 仓库视图都会遇到许多尖锐的边界问题。因此，Spokes 付出了很高的复杂度成本，以确保系统始终完全一致。下面看看这具体意味着什么。

Spokes 是一个*基于共识*的分布式系统。它会在不同服务器上保存 Git 仓库的多个副本。每当你推送新数据，协调器就把推送扇出，让仓库的每个实例都收到一份。这个扇出过程与一种经典共识算法 [3PC（三阶段提交）](https://en.wikipedia.org/wiki/Three-phase_commit_protocol)同步：只有多数节点确认后，推送才会被接受。

![一个协调器与五个参与者执行三阶段提交](/assets/images/cursor-git-at-any-scale/03-three-phase-commit.svg)

在进一步讨论 Spokes 如何使用 3PC 之前，需要先理解 Git push 的工作方式。一次 Git push 包含两部分：一个 *packfile* 和一次*引用事务*。前面已经介绍过的 packfile 保存本次推送到仓库的对象，包括变更中的 blob、tree 和 commit。真正发布变更的是事务：它会更新一个或多个引用，例如当前工作的分支，使其指向刚推送的提交。

这种分离在这里非常方便，因为在指向某个提交的引用更新之前，该提交对外并不可见，用 Git 的术语说就是不可达。因此，可以先把 packfile 同时扇出到所有主机——这一步不需要同步——然后再对引用事务执行三阶段提交。引用事务比 packfile 小得多，同步速度也快得多。Git 本身支持预备引用事务：它可以获取引用锁，验证现有值是否符合预期，然后一直持有锁，直到收到提交或中止事务的命令。

![packfile 上传和引用事务在副本间通过 3PC 协调](/assets/images/cursor-git-at-any-scale/04-spokes-push-fanout.svg)

采用这种设计，每次推送都能在所有副本间完全同步。读取操作，也就是 fetch 和 clone，随后可以安全地路由到*任意单个副本*，因为所有副本始终处于最新状态。

这基本就是 Spokes 的工作方式，而且它在过去 13 年里一直运行得相当不错。当然，Spokes 并不完美，没有任何系统是完美的。到了 2026 年，人们使用 Git 仓库的方式发生了巨大变化，我们也在构建分布式系统的过程中学到了许多重要经验。时间和实践已经说明，Spokes 的哪些选择确实最优，哪些并不是。

其中一个后来变得非常关键的缺陷，是 **3PC 的横向扩展能力受限**。Spokes 刚发布时，每个仓库三个副本是一个理想平衡点。三个副本足以承载普通仓库且留有余量，即使一台机器宕机，也还有足够冗余继续接受推送。

2026 年的情况已经很不一样。企业的普通仓库如今往往是庞大的 monorepo。三个副本不足以承载这类仓库的流量，尤其是 CI 流量。Spokes 当然可以运行三个以上的副本，真正的障碍是令人畏惧的[规模化尾延迟](https://cacm.acm.org/research/the-tail-at-scale/)。三阶段提交与 Git 的事务模型结合得非常优雅，但作为共识算法，它存在根本限制：每一个步骤的延迟，都取决于集群中最慢的服务器。集群加入的副本越多，推送吞吐量就越差。

这个扩展约束也会反向生效。Agent 大规模处理 Git 仓库时，常常不在 monorepo 中工作，而是创建海量小型仓库，其中很多是临时的，大多数也很少被访问。Spokes 在这里同样力不从心，因为每个仓库仍然需要三个副本。三个几乎空闲的副本又不能缩减，否则系统将无法保持完全一致，并可能丢失数据。使用三阶段提交时，下限总是太高，上限又太低。

另一个缺陷在设计之初很难预见，但真正经历后会感受得格外明显：大规模运维 Spokes 可能相当艰难。磁盘上的仓库始终是共识的事实来源，因此每个仓库的每个副本都*极其重要*。你必须把仓库当作*宠物，而不是牲畜*。

这首先意味着，必须准确知道每个仓库在哪里。系统因而依赖一个外部数据库，其中维护着一张巨大的路由表，把每个仓库映射到它所在的每台机器。这既增加了依赖，也引入了潜在的可用性问题。每个仓库还必须计算校验和，并在路由表中持续更新这些校验和，确保磁盘上的仓库仍然有效。一旦仓库出现异常——相信我，坏事经常发生，Git 在实践中相当挑剔——系统就必须发现问题并调度修复任务，让仓库恢复健康，而且必须非常快。因为磁盘仓库就是事实来源，损坏的副本与缺失的副本一样糟糕。三个副本中有两个损坏时，系统就无法继续接受推送，因为已经无法形成法定多数。

## Continuity

Continuity 是 Cursor 开发的 Git 存储系统。它的思路很清楚：吸收 Spokes 做对的一切，同时修复经过多年实践后已经明确的问题。

*Continuity* 是一个简单的系统——系统如果不简单，就不可能易于运维。它背后的核心原语是一份预写日志，也就是 WAL，存储在兼容 S3 的对象存储中。生产环境直接运行在 S3 上，但系统设计允许部署到任何云平台。

仓库收到推送时，Continuity 会把它作为 WAL 条目写入 S3。**只有推送已经完整持久化，系统才会返回确认。** 每次推送都存为独立对象：推送的 packfile 会同时写入磁盘并上传到 S3。不过，上传 WAL 条目并不等于发布它。只有当系统在仓库的本地副本上成功预备引用事务，并在 WAL 索引文件中记录一个指向该条目的指针后，推送才变得可见。WAL 索引本身也是对象存储中的一个对象。**这迫使所有推送都具备线性一致性。**

![Continuity 将一次推送写入 WAL 并更新索引](/assets/images/cursor-git-at-any-scale/05-continuity-wal-push.svg)

Continuity 会尽量避免每次推送只执行一次独立的 S3 写入，因为在繁忙仓库中，S3 PUT 的延迟会直接成为推送吞吐量的硬上限。通过精心调优的批处理实现，再加上只需让引用事务与一个本地仓库同步，而不是与副本法定多数同步，系统能够以磁盘所允许的速度接收推送。

本地仓库当然是存储在高速 NVMe 上的普通 Git 仓库。这里沿用了 Spokes 的做法，因为我认为 Spokes 在这点上完全正确。这让我们能够复用 Git 社区出色的开源成果，包括上游 Git 客户端及其众多性能优化；团队可以专注于交付新功能，而不是折腾 Git 的特殊实现。

### 共识

前面看到，Spokes 集群难以运维的一个原因，是必须准确跟踪每个服务器上每个仓库的位置。*Continuity* 的处理方式完全不同。每个仓库究竟位于哪里？答案是：“任何地方。” 这并不重要。Continuity 把仓库视为磁盘上的温缓存，事实来源永远是 S3 中的预写日志。系统是无状态的，不存在路由表，也不需要运维关系型数据库——谢天谢地。如果某台主机被访问时，本地磁盘上没有对应仓库，系统就从 WAL 将其物化出来。这个过程可以非常高效，但当然不希望*每次*都这样做，因为那会浪费资源。生产环境使用[最高随机权重哈希，也称 Rendezvous Hashing](https://en.wikipedia.org/wiki/Rendezvous_hashing)，把仓库 ID 映射到预期承载它的节点列表。路由仓库所需的全部状态，只有仓库 ID 和集群当前的健康节点集合。即使这些状态不同步，例如某个节点变得不健康，也完全没关系，系统只需在排序中的下一个节点上物化仓库。

那么共识呢？选举呢？某个仓库的主节点是哪台服务器？同样不重要。这里没有状态，也没有共识。任何服务器都可以成为主节点。对预写日志的所有更新，都通过 S3 上的原子比较并交换操作，也就是 CAS 来同步，所以仓库的任意实例接收推送都是安全的。与路由一样，让任意服务器临时充当主节点并不是最高效的做法，因为它会导致 CAS 重试并拖慢推送。因此，实际运行时总会选择同一台服务器作为主节点，也就是 Rendezvous Hashing 排序列表中的第一台。但在部署、故障转移或短暂网络异常等边缘场景中，究竟哪台服务器是主节点并不重要。系统被设计为：降级时始终正确，健康时始终快速。

![两个前端通过 S3 条件写入竞争更新 WAL 索引](/assets/images/cursor-git-at-any-scale/06-s3-cas-race.svg)

### 复制

把预写日志放在 S3 中，为扩展打开了巨大的可能性。系统可以拥有*任意数量*的副本，因为 S3 的扩展能力无与伦比，所有副本都直接从 S3 追赶进度。Continuity 采用乐观复制，在集群中发送 gossip UDP 数据包。每次推送后，数据包都包含副本直接从 S3 追赶进度所需的全部元数据。“这也太疯狂了，”我仿佛听见跨越时空、屏幕另一端的你低声说，“UDP 并不是可靠传输。” 它当然不可靠。分布式系统里没有什么是可靠的：线路不可靠，路由不可靠，拓扑也不可靠。但这没有关系。每个副本都知道自己上次同步的 WAL 索引版本对应的 ETag。在副本上执行读取操作时，系统会携带预期 ETag 向 S3 发起条件 GET。如果收到不带响应体的 304，说明副本已经是最新状态，可以立即处理 fetch 或 clone；这个只涉及 S3 元数据的操作通常几乎瞬间完成，平均少于 10 毫秒。如果返回 200，响应中就包含最新的 WAL 索引版本，副本会先据此追上进度，再提供读取服务。

![UDP gossip 丢失时，副本仍通过 S3 条件读取恢复一致](/assets/images/cursor-git-at-any-scale/07-wal-replication.svg)

复制用的 UDP 数据包即使丢失，或者因为拓扑变化到达了错误的服务器，也没有关系。所有副本上的全部读取都保持完全一致，因为它们会与事实来源 S3 进行校验。系统被设计为：降级时始终正确，健康时始终快速。

这带来两方面影响。第一，因为系统始终一致，在它之上构建基础设施非常简单。我们——包括 Agent、Web 界面和客户端——看到的始终是仓库的全局一致视图。第二，因为系统能够同时向上和向下扩展，每个仓库都可以获得恰到好处的副本数量。大型 monorepo 可以部署到数百个副本，以承载全部 CI 任务流量；Agent 创建的数百万个小型仓库，每个只需一个副本。由于 S3 才是事实来源，并不需要更多副本来确保可用性。事实上，空闲仓库连一个副本都不需要：某个副本长时间没有流量时，系统会从节点磁盘上回收它；下次 fetch 到来时，再从 WAL 物化即可。

![Continuity 根据仓库流量动态调整副本数量](/assets/images/cursor-git-at-any-scale/08-elastic-replicas.svg)

### 压缩

预写日志需要定期压缩。日志不能无限增长，因为完整恢复要重放每个条目；条目越多，恢复成本就越高。

巧合的是，普通 Git 仓库同样需要定期压缩，尽管 Git 本身并不以 WAL 为基础。前面已经看到，Git 仓库的基本存储单元是 *packfile*。每次向远程仓库推送，或向本地仓库 fetch，都会创建一个新的 packfile。这个过程无法无限持续：每个 packfile 都有自己的索引，可以高效查找其中包含的对象，但这种查找只在单个 *packfile* 内高效。如果要查找一个特定对象，而仓库里有 100 个 packfile，就必须依次打开每个索引并查找，直到在其中一个 packfile 中找到对象。一项高效操作如果必须执行数百次或数千次，也就不再高效。

现代 Git 已经很擅长缓解这个问题，现在支持多 pack 索引和增量几何压缩。但最终仍然必须硬着头皮，对磁盘上的 Git 仓库重新打包。历史上，这一直是 Spokes 等系统的可用性隐患。重新打包即使以增量方式执行，也非常消耗 CPU，而且必须在系统的所有副本上进行。若不小心在同一仓库的两个或更多 Spokes 节点上同时触发维护操作，很容易导致仓库发生故障转移。

Continuity 会摊薄压缩成本。只有主节点执行压缩，压缩结果同时应用于磁盘仓库和 WAL。由于所有副本都跟随 WAL，它们也会跟随压缩事件。副本无需自行重新打包，只需从 S3 下载已经压缩的 pack，以带宽换取 CPU。

![增量 WAL 压缩及压缩结果向副本传播](/assets/images/cursor-git-at-any-scale/09-wal-compaction.svg)

### 规模

复制和压缩，是决定 Git 存储系统在负载下表现的两个关键因素。正如刚才看到的，两者内在相关：仓库每秒接收的推送越多，读取性能下降得越明显，因为每次推送产生的 packfile 都必须经过压缩，Git 操作才能保持高效。如果还要复制这些推送，那么压缩结果也必须被复制，或者由每个副本独立执行压缩。

*Continuity* 的 WAL-first 设计提供了**完全一致的横向扩展能力**：可以部署任意数量的副本，只读 Git 操作的吞吐量会随副本数量线性增长。因为集群中的所有副本都完全一致，系统不仅能扩展 Git 协议层的 clone 和 fetch，也能扩展 Origin 在仓库之上执行的所有 RPC 操作，包括 Web 界面交互、REST API 和各种 Agent 接口。

我们已经在最多 100 个副本上进行了合成压力测试，读取吞吐量始终呈线性扩展，推送吞吐量没有出现退化。

集群的推送吞吐量取决于更新 S3 中 WAL 的延迟。使用 S3 Standard 时，在持续压缩并把压缩数据复制到所有其他节点的同时，系统最多可维持每秒 120 次推送。我们也在 S3 Express One Zone 上部署了高性能集群，它的 PUT 延迟要低得多。在那里，系统每秒可以接收超过 300 次推送，瓶颈实际上变成了 Git 压缩磁盘数据的速度。我们正在研究新的磁盘数据布局方式，以降低压缩的影响。目标是在不放松严格耐久性和一致性保证的前提下，继续提升 Git 仓库接收代码的速度。

原文图表比较了 S3 Standard 与 S3 Express One Zone 在 Cursor 的 monorepo `everysphere` 上的推送和 clone 吞吐量。所有推送都会在返回确认前实现线性一致并持久化到外部存储；所有 clone 都保持完全一致。

### 以 WAL 为事实来源

S3 是一项很出色的技术。由 S3 API 开创的 blob 存储概念，已经被证明是构建大型数据存储系统的强大基础，这一点显然同样适用于 Git 仓库托管。本文介绍的设计在很多方面都有创新，但它并不是第一个把 packfile 存为 blob 的系统。Azure DevOps——微软自家产品 GitHub 的微软自家竞争对手——就拥有一个非常成功的 Git 存储系统：packfile 存储在 blob 存储中，引用存储在关系型数据库 MS SQL Server 中。这样的系统存在许多权衡。关系型数据库很适合扩展大型引用事务，但你也因此必须运维一个关系型数据库。我们坚信，Git 数据的一致性比其他任何考虑都更重要。正是这一点最终促使我们设计了不依赖外部数据库的 WAL 系统。

生产环境中的 Git 仓库可能出现许多问题：静态数据损坏、重新打包时的缺陷、推送过程中的竞态。它就是一大堆边界情况的集合。Git 上游已经解决了其中大部分问题，但不是全部。任何系统都会有缺陷，即使它是开源且被广泛部署的系统也不例外。Continuity 的一致性模型确保可以跟踪仓库发生的每一个基础操作。**只有推送完整持久化到 WAL 后，系统才会返回确认；所有推送都被线性化；访问任意仓库时，看到的每个视图都始终完全一致。** 因为每次推送都在 WAL 中，所以可以查看仓库曾经经历的每一种状态。系统拥有所有推送以及所有重新打包操作的完整来源记录，可以让任意副本向前或向后移动；也不必与任何外部数据库同步状态，无论那个数据库只存引用，还是存储全部对象数据。当——不是“如果”——我们遇到 Git 中的缺陷时，就能精确定位发生了什么并将其回退。除了 Git 已有的缺陷，Continuity 自己引入的新问题很少，因为整个过程中所有 Git 操作都使用现成工具，在磁盘上的普通 Git 仓库中完成。

## Origin

我们非常清楚，托管他人的源代码有多么重要。我想，每一位读懂本文的人也都同样清楚。如果开发者无法向 Git 仓库推送或拉取代码，一家公司可能会陷入停摆。CI 系统停机五分钟造成的生产力损失很难用美元精确衡量，但无论用什么标准看，都会是一个极其庞大的数字。

Agent 从根本上改变了我们处理软件的方式，并且在许多方面加剧了这个问题：更多代码、更多 PR、更多 CI 运行。版本控制位于这一切的核心，同时也可能是最难在一夜之间更换的部分。

几个月来，我们在 Cursor 内部一直面对这些困难，也投入了大量思考与精力，构建出一个既能解决自身问题，也有望解决客户问题的平台。当前重点是提供一条尽可能顺畅的迁移路径，让用户获得更高的可靠性、性能和扩展能力，同时把迁移的痛苦降到最低。

Origin 不是一项实验。它凝聚了团队成员数十年来构建同类系统的经验，这些人深刻理解其中挑战的分量。我们拥有已经得到实践验证的工程与运维理念，也坚定承诺：随着版本控制生态继续演进，我们会持续推动它发展。

我们希望，你愿意把信任交给我们和我们的平台。
